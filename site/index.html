The complete workflow

From a Slack request
to a reviewed PR.

You shape the intent. Agents handle the build, checks and reviews. Your team decides what gets merged.

Read the workflow guide
  1. 01

    Describe the task.

    Ask in your project’s Slack channel. Add the issue link and context. Rovara suggests Quick or Full; the task owner starts the work.

    Starts withYour explicit request
  2. 02

    Agree on the plan.

    Quick has one coding-plan approval. Full adds requirements and design approvals. Teammates add context; the owner approves the current version and check scope.

    You approveThe approach and checks
  3. 03

    Work in the cloud.

    The agent implements the approved plan in the project’s workspace in your AWS account. The branch, files and conversation stay with the task.

    Agents produceA working branch
  4. 04

    Test and review.

    Required and selected tests or checks run on the changed code. Separate code and security reviews follow. Blocking findings can go back to coding, then fresh checks.

    You can inspectResults and review findings
  5. 05

    Review the draft PR.

    When the selected checks and reviews pass, Rovara opens a draft PR of the checked code and posts it in Slack. Review the diff and repository CI in GitHub.

    Your team decidesWhat gets merged
  6. 06

    Keep the work moving.

    PR comments become proposed fixes. Approve the changes you want; agents update the same PR after fresh checks and reviews. Return to the retained workspace for follow-ups.

    Stays connectedThe thread, workspace and PR

Before your first task

A few practical questions.

Planning, testing and the workspace behind your Slack conversation.

When should I use Quick or Full?

Use Quick for a well-defined fix or feature: approve a coding plan, then let the work run. Full adds requirements and design approvals before the coding plan, so your team can resolve unclear behavior and implementation choices first. Both keep the project’s required checks and reviews.

Explore the planning paths
What does “tested” mean for my task?

Checks follow the approved plan and project configuration. Results identify what ran on the changed revision, with passed, failed or unverified outcomes. Code and security reviews run in separate read-only sessions. End-to-end coverage depends on the project’s tests and qualified runtime; missing required coverage stays visible.

The example above uses synthetic rows and a mocked database. It does not show a browser test or a recorded customer run.

Understand checks and review evidence
Where does the work live when I leave?

In your AWS account. Each task has an isolated cloud worker and a persistent encrypted workspace. Idle compute stops; files and conversation stay on the workspace disk so the next mention can resume. AWS compute, retained storage and model usage have costs.

How workspaces stop and resume
What happens when a reviewer asks for changes?

Rovara reviews the PR comments and brings recommendations back to the Slack thread. The task owner approves the fixes to make, answers questions or dismisses feedback. Approved fixes go through checks and separate reviews again before updating the same PR. Your team controls the merge in GitHub.

Follow the PR feedback loop
Can I keep using my coding tools and model access?

Yes. Claude Code, Codex and Cursor can start or continue tasks through Rovara’s MCP tools. Model access is configured for your workspace. An administrator can also enable your own ChatGPT Plus or Pro plan for your own tasks; that option is off by default.
